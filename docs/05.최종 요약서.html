1. 개요

항목내용
배경와썹하우스의 소셜 다이닝 "우연한 식탁"은 저녁 회차마다(기획 기준 매주 목요일) 처음 보는 4~6명이 함께 저녁을 먹는다. 지금은 신청 폼·입금 확인·조 편성·식당 예약·단체방 초대·리마인드를 운영자가 손으로 한다.
목표신청부터 피드백까지를 자동화하고, 운영자는 자동으로 해결되지 않은 예외만 처리하게 한다.
범위참가자 모바일 웹(PWA) + 운영자 웹 어드민. 결제·환불은 모의 처리, 문자·알림톡은 제외(사업자 인증 채널 필요).
결과필수 기능 77건 모두 구현, 데모 12단계가 배포본에서 끊김 없이 동작. 테스트 케이스 28건(통과 27·부분 1), 단위 테스트 19건 통과.

한눈에 보는 흐름

신청·결제→ 마감 시각 자동 매칭→ 재배치·확정 / 실패 안내→ 식당 배정·단체방·알림→ 전날 리마인드·대화 주제→ 체크인·노쇼→ 피드백 → 다음 매칭 반영

3. 아키텍처

설계 원칙내용
상태는 DB 함수로만 바꾼다신청·결제·매칭 적용·환불·체크인 등 모든 상태 변경은 security definer 함수 하나가 한 트랜잭션으로 처리하고 상태 변경 이력을 남긴다. 함수는 일반 사용자 권한에서 실행을 막고, 서버가 로그인·본인 확인 후 호출한다.
두 번 실행돼도 안전하게스케줄러 작업은 job_runs의 작업 키로, 알림·메시지는 dedupe_key로 한 번만 만든다. 스케줄러와 운영자 즉시 실행이 겹쳐도 결과가 같다.
매칭 엔진은 순수 함수후보·관계·설정을 받아 테이블·실패·이벤트를 돌려주는 함수라 단위 테스트와 저장 없는 미리보기가 가능하다. 적용은 DB 함수가 한 번에 한다.
알림은 원장 + 대기열모든 알림은 notifications에 쌓이고, 트리거가 참가자 설정에 따라 웹 푸시·이메일 발송 행을 만든다. 발송기는 1·2분 간격으로 재시도하고 3회 실패하면 예외 처리함으로 넘긴다.
개인정보 최소 노출같은 테이블에는 이름·연령대·MBTI·관심사·한 줄 소개만, 식사 조건은 이름 없이 인원수로만 공유한다. 운영자도 참가자끼리의 대화 내용·개수는 볼 수 없다.

4. 매칭 알고리즘

  1. 대상 선별 — 해당 회차에 결제를 마친 활성 신청. 참가 제한자·결제 기한 초과자는 제외.
  2. 필수 조건 — 지역별로, 나이 차이 8살 이내의 묶음을 만들 수 없는 사람은 먼저 제외(완화하지 않음). 차단·신고·불편함 관계는 같은 테이블 금지.
  3. 테이블 구성 — 한 지역만 고른 사람으로 먼저 4~6명 테이블을 만들고, 배치가 가장 어려운 사람부터 선호 점수(성비 30·MBTI 25·관심사 20·원하는 성향 15·새로운 사람 10)가 높아지는 사람을 채운다.
  4. 재배치·병합 — 남은 사람은 자신이 고른 다른 지역의 빈자리로 옮기고(재배치 기록), 그래도 남으면 남은 사람끼리 새 테이블을 만든다.
  5. 두 계획 비교 — "한 지역 선택자 우선" 계획과 "전원 동시" 계획을 모두 계산해 더 많이 앉히는 쪽을 고른다. 같으면 1인당 점수가 3점 이상 높을 때만 바꾼다.
  6. 확정·실패 — 최소 점수 60 이상이면 자동 확정. 실패자는 사유(인원 부족·나이·관계·점수)와 함께 다른 날짜 대기 또는 대체 일정·보관·환불을 안내한다.

피드백 반영: 함께 앉았던 사람은 "새로운 사람" 점수에서 감점되지만, 다시 만나고 싶다고 고른 사람은 감점하지 않는다. 불편함·신고는 이후 동석을 막는다.

5. 트러블슈팅

문제원인해결
재배치가 한 번도 기록되지 않음모든 사람을 첫 단계에서 한꺼번에 배치해, 여러 지역을 고른 사람이 "옮겨 간" 기록이 생기지 않았다.한 지역 선택자로 먼저 테이블을 만들고 여러 지역 선택자를 빈자리로 재배치. 두 계획 중 더 많이 앉히는 쪽을 고르게 해 무작위 신청자 40세트 비교에서 배정 성공률이 45.4% → 47.6%로 올랐다.
단체방 메시지 순서가 뒤섞임한 트랜잭션에서 넣은 메시지가 모두 같은 now() 시각을 가져 정렬이 무작위가 됐다.메시지 시각 기본값을 clock_timestamp()로 바꿔 넣은 순서대로 정렬.
시연을 반복하면 실패 시연이 사라짐되돌리기가 매칭 결과만 지우고, 실패자가 고른 일정 이동·보관·환불은 남겨 두었다.되돌리기가 이동한 신청 삭제, 이용권 장부 원복, 환불 취소까지 하도록 확장.
데모 데이터 삭제가 막힘발송 이력이 알림·메시지를 외래키로 참조해 되돌리기에서 삭제가 거부됐다.발송 이력의 외래키를 on delete cascade로 변경.
화면이 느림 (화면당 1~3초)DB는 서울인데 Vercel 함수가 기본값인 미국 동부(iad1)에서 실행돼, 화면당 5~15번의 쿼리가 매번 태평양을 왕복했다.vercel.json에서 함수 지역을 서울(icn1)로 고정하고, 화면 이동 시 바로 뜨는 로딩 화면 추가. 스케줄러 1회 3.5~5.5초 → 0.7~1.2초.
시간이 지나면 시연 장면이 바뀜스케줄러가 예정 시각마다 리마인드·시작·종료·매칭을 실행해, 심사 시점에는 확정·실패 장면이 지나가 버린다."자동 진행 멈춤" 회차는 모든 예약 단계를 건너뛰고, 운영자 진행 단계 버튼으로만 움직이게 함.
과거 회차에 단체방이 없음과거 22개 회차 이력을 시드로 바로 넣으면서 확정 단계(식당·단체방·안내)를 거치지 않았다.과거 테이블마다 실제 흐름과 같은 시각의 안내·리마인드·대화 주제·참석자 대화를 채우는 seed:rooms 추가.
웹 푸시가 아이폰에서 안 옴iOS는 홈 화면에 설치한 웹앱에서만 푸시를 받는다.PWA 매니페스트·서비스 워커를 넣고, 미설치 아이폰에는 "홈 화면에 추가" 안내를 띄움.

7. 한계와 다음 단계

  • 실결제 — 지금은 모의 결제·환불. PG(토스페이먼츠 등) 연동 시 결제 함수의 상태 전이는 그대로 쓰고 승인·환불 호출만 붙이면 된다.
  • 메시지 채널 — 카카오 알림톡·문자는 사업자 인증이 필요해 제외했다. 발송기가 채널별로 분리돼 있어 채널 추가가 쉽다.
  • 이메일 발신 주소 — 무료 범위에서 Gmail SMTP를 썼다. 도메인을 확보하면 발송 모듈 한 곳만 바꿔 서비스 도메인 주소로 보낼 수 있다.
  • 회원가입 — 해커톤 범위에 맞춰 테스트 계정 로그인만 제공한다.
  • 매칭 고도화 — 지금은 탐욕 배치 + 두 계획 비교. 신청자가 많아지면 지역 간 교환 탐색이나 최적화 기법으로 성공률을 더 올릴 수 있다.
  • 웹 푸시 실기기 검증 — 발송 경로까지 확인했고 실제 기기 수신은 추가 확인이 필요하다.
