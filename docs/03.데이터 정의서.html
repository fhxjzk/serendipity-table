1. 문서 개요

항목내용
목적기능 86건이 읽고 쓰는 데이터를 테이블 44개(필수 40, 추가 4)·컬럼 379개로 정의하고, 관계(ERD)·제약·권한·가상데이터 적재 규칙을 정해 DB를 바로 만들 수 있게 한다.
정한다테이블과 컬럼, 자료형, NULL 여부, 기본값, 값 제약, PK·FK·UNIQUE, 멱등 규칙, 코드값, 테이블별 접근 권한, 가상데이터 정제·적재 규칙, 시연 데이터 구성
정하지 않는다RLS 정책의 SQL 문장, DB 함수 본문, 매칭 알고리즘의 점수 계산 방식(A3 매칭 엔진에서 확정)
이름 규칙테이블·컬럼은 소문자 snake_case. 테이블은 복수형으로 쓰되 이력·원장 성격은 단수형(ticket_ledger·status_history). PK는 id(uuid), FK는 대상_id, 코드값은 대문자 영문(MATCH_CONFIRMED). SQL 예약어와 겹치는 "table"은 dining_tables로 부른다.
함께 만든 파일같은 정의에서 생성한다 — 03-1.전체 ERD(44개 테이블 통합 ERD, eXERD 역공학 원본 그림), erd/usangtak_erd.exerd(eXERD 모델 원본)·erd/usangtak_erd.png(그림),sql/schema_draft.sql(Supabase용 DDL·한글 주석·코드 시드, 프로젝트 생성 후 실행해 검증), sql/schema_mysql_for_exerd.sql(eXERD 역공학용 MySQL DDL, 한글 주석이 논리명이 된다)

2. 설계 원칙

원칙내용
상태 4종 분리applications에 application·payment·match·attendance 상태를 따로 두고, 바뀔 때마다 status_history에 시각·주체·원인·이전 값을 남긴다.
멱등 키자동 작업은 job_runs.job_key·match_runs.run_key, 결제는 idempotency_key, 알림·예외·시스템 메시지는 dedupe_key에 UNIQUE를 걸어 다시 실행해도 결과가 늘지 않는다.
중복 배치 금지table_members에 (회차, 참가자) 부분 UNIQUE를 걸어 같은 회차의 두 테이블에 동시에 앉을 수 없다.
쓰기는 서버 함수로참가자는 상태 컬럼을 직접 바꾸지 못한다. 신청·결제·취소·매칭·환불은 DB 함수(트랜잭션)나 서버 API가 처리하고, RLS는 읽기 범위를 막는다.
선택값은 코드관심사·성향·지역·가격대는 code_values의 코드로 저장한다. 화면 선택지와 가상데이터 정제가 같은 코드를 쓴다.
신청과 회차신청 한 건이 날짜 × 지역 조합(application_choices)을 여러 개 가진다. 각 회차의 매칭은 그 회차를 고른, 아직 배치되지 않은 신청만 후보로 삼고, 고른 마지막 회차까지 배치되지 않으면 ALTERNATIVE_OFFERED가 된다.
기록은 지우지 않음취소·이동·재배치는 행을 지우지 않고 상태나 left_at으로 남긴다. 처리 사유와 지표를 다시 계산할 수 있어야 한다.
시각과 금액시각은 timestamptz(저장 UTC, 화면 KST), 날짜는 date, 금액은 원 단위 정수.

3. ERD

원본은 44개 테이블과 모든 FK를 한 장에 담은 「03-1. 전체 ERD」다. 03-1은 이 문서의 DDL을 eXERD로 역공학해 만든 그림이며, 모델 파일(erd/usangtak_erd.exerd)을 eXERD에서 열어 확대·편집할 수 있다. 이 장은 읽기 쉽게 영역별로 잘라 낸 보기이며, 전체 44개 테이블을 세 장으로 나눠 그렸다. 상자에는 PK·FK 컬럼만 보이고, 선은 FK 관계다(N 쪽이 FK를 가진 테이블, 1 쪽이 참조되는 테이블). 같은 테이블이 여러 장에 나오며, 상자를 가로지르는 일부 선과 운영자 기록용 FK(created_by·decided_by 등)는 생략했다. 전체 관계는 5장의 FK 표기로 확인한다.
