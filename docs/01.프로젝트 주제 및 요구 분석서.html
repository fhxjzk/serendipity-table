1. 프로젝트 개요

항목내용
프로젝트명우연한 식탁 MVP
서비스 주제처음 보는 4~6명을 결이 맞는 사람끼리 한 테이블로 연결하는 소셜다이닝 서비스
운영사와썹하우스 — 2025년 4월부터 20~30대 대상 오프라인 모임 150회 이상, 누적 참가자 1,600여 명, 만족도 4.8/5, 재방문율 25%
개발 형태참가자 화면은 모바일 우선 반응형 웹(휴대폰·PC 브라우저 공용), 운영자 화면은 PC 기준 웹 어드민으로 만들고 하나의 Next.js 앱으로 제공한다(ADR-001). 홈 화면에 설치해 앱처럼 쓰는 PWA를 이번 범위에 포함하고, 이후 웹뷰 앱으로 감싸 배포하거나 백엔드를 유지한 채 네이티브 앱을 추가하는 방식으로 앱 서비스로 확장한다.
주요 사용자참가자(20~30대 신청자), 와썹하우스 운영자
서비스 목적신청 → 결제 → 자동 매칭 → 자동 재배치 → 자동 확정 → 식당·단체방 안내 → 참석 → 피드백 → 다음 매칭을 하나의 제품 흐름으로 연결한다. 정상 흐름은 운영자 개입 없이 끝나고, 운영자는 자동 처리가 불가능한 예외만 처리한다.

2. 현재 운영 방식과 문제점

2.1 현재 운영 방식

Google Forms 신청서 작성 → 운영자 수기 매칭 → 행사 2일 전 카카오톡 단체방 생성·식당 안내 → 행사 1일 전 리마인드 문자 → 식사 → 단톡방 대화 콘텐츠 제공 → 개인별 만족도 피드백 → 다음 매칭에 참고

MVP 성과(2026년 6~8월, 소액 메타 광고): 총 신청 243건 · 실제 참가 142명(전환율 58.4%) · 재방문 22명(재방문율 15.5%) · 결제 매출 1,264,000원

2.2 문제점

대상문제이 프로젝트의 해결 방향
참가자신청 후 결제·매칭·확정 상태를 실시간으로 알 수 없다홈 화면에서 4종 상태와 다음 일정 표시 (R-06)
신청 후 결제·확정까지 기다리는 동안 이탈한다상태 변화 시점별 알림, 결제 기한 안내 (R-16, R-26)
취소·환불하려면 운영자에게 문자로 계좌를 보내야 한다원결제수단 자동 환불(모의) (R-08)
매칭이 안 되면 대체 날짜·지역을 다시 신청하기 번거롭다대체 일정 추천과 원클릭 일정 이동 (R-07, R-08)
이전 참가 만족도가 다음 매칭에 반영되었으면 한다피드백·사람별 선호를 다음 매칭에 반영 (R-25)
운영자Google Forms·입금 문자·카카오톡·식당 예약을 일일이 수기로 처리한다신청·결제·식당 배정·단체방·안내를 한 시스템에서 자동 처리
지역·연령·성비·MBTI·관심사를 동시에 고려하는 수기 매칭이 번거롭다필수 조건 + 선호 점수 기반 자동 매칭 (R-17~R-21)
신청자가 늘수록 조합 경우의 수와 누락 가능성이 빠르게 증가한다확정 전 필수 조건 재검증, 멱등 실행 (R-18, R-23)
개인별 피드백과 이전 만남 이력을 다음 매칭에 반영하기 어렵다참석·피드백·만남 이력 저장과 반영 (R-12~R-13, R-25)
CS를 자동화하고 싶다상태·실패 사유·다음 행동을 참가자 화면에서 바로 안내, FAQ·문의 자동 답변 (R-06, R-07, R-22, R-48)
예약 변경·취소·노쇼가 테이블 전체에 영향을 주고 CS로 이어진다취소 시점별 처리, 확정 후 취소 재배치, 노쇼 이력 기록 (R-15, R-27, R-37)

3. 대상 사용자

사용자사용자 상황필요한 점
참가자새로운 사람을 만나고 싶지만 자연스러운 계기가 부족하다나와 결이 맞는 사람과 한 테이블에 앉을 수 있어야 한다
신청하고 결제했지만 결과를 기다리는 중이다지금 상태와 결과 발표 시점을 한 화면에서 알 수 있어야 한다
원하는 날짜·지역에 매칭되지 않았다이유를 알고 다른 일정 이동·보관·환불을 직접 고를 수 있어야 한다
처음 보는 사람과 식사하는 것이 어색하다식당·시간 안내와 대화 주제·아이스브레이킹을 받을 수 있어야 한다
모임이 좋았거나 불편했다사람별 선호와 신고를 안전하게 남기고, 다음 매칭에 반영되어야 한다
운영자매주 목요일 저녁 회차를 운영한다회차·지역·정원·마감 시각과 식당 재고를 미리 설정해 두면 나머지는 자동으로 진행되어야 한다
모든 테이블을 일일이 검수할 시간이 없다자동 처리 결과를 모니터링하고, 해결되지 않은 예외만 처리할 수 있어야 한다
안전 문제가 생길 수 있다신고를 검토하고 참가 제한을 기록할 수 있어야 한다

4. 주요 요구사항

R-번호는 이 프로젝트의 요구사항 번호이고, 오른쪽 열은 대응하는 PRD 기능 ID다. PRD의 P0는 필수, P1과 PRD 기능을 확장한 항목(R-47~R-49)은 추가, P2와 일부 P1은 제외 범위(6.3)로 분류했다.

4.1 필수 — 참가자

번호요구사항PRD ID
R-01참가자는 테스트 계정으로 로그인하고 이름·연락처·출생연도·성별·직업을 입력·수정할 수 있어야 한다.ACC-01, ACC-02
R-02참가자는 MBTI·관심사·본인 성향·만나고 싶은 사람의 성향을 복수 선택하고, 희망 식사 가격대·못 먹는 음식·알레르기와 같은 테이블 참가자에게 보여 줄 한 줄 소개(선택, 30자)를 입력할 수 있어야 한다.ACC-03, ACC-04
R-03참가자는 개인정보 수집·이용과 운영 정책에 동의해야 신청할 수 있어야 한다.ACC-05
R-04참가자는 모집 중인 회차(날짜·시간·지역·신청 마감일)를 확인하고, 참가 가능한 날짜와 희망 지역을 복수 선택해 필수 항목 검사 후 신청할 수 있어야 한다.APP-01~03
R-05참가자는 1회권 또는 구독 이용권을 선택해 모의 결제할 수 있어야 하며(구독은 잔여 횟수를 만들고 신청마다 1회씩 자동 차감, 보유한 보상 쿠폰은 결제 시 자동 적용), 결제 전과 신청 완료 화면에서 환불 규정(진행 2일 전부터 환불 불가, 당일 취소와 단체방 퇴장 불가, 당일 불참·노쇼 기록 정책)을 확인할 수 있어야 한다.APP-04, PAY-01, PAY-02
R-06참가자는 홈 화면에서 신청·결제·매칭·참석 상태와 매칭 발표 예정 시점, 다음 안내 일정을 확인할 수 있어야 한다.STA-01, STA-02, PAY-01
R-07매칭에 실패한 참가자는 실패 이유와 가능한 대체 날짜·지역을 확인하고, 일정 이동·이용권 보관·환불 중 하나를 선택할 수 있어야 한다.STA-04, STA-05
R-08대체 일정을 선택하면 기존 결제를 유지한 채 새 회차의 매칭 대기로 전환되고, 환불을 선택하면 운영자 승인 없이 원결제수단으로 환불(모의 상태 전환)되어야 한다. 구독 이용권으로 신청한 경우에는 환불 대신 이용권 1회를 자동으로 복원한다.STA-06, PAY-03
R-09테이블이 확정되면 참가자는 즉시 앱 내 알림·웹 푸시(설정 시 이메일)로 결과를 받고, 식당명·주소·지도 링크·집합 시간·예약명·식사 가격을 확인할 수 있어야 한다.INF-01, INF-03
R-10참가자는 확정과 동시에 생성된 앱 단체방에 자동 초대되어 시간·장소, 테이블 조합 큐레이션, 취소 정책 공지를 확인하고 실시간으로 대화할 수 있어야 한다. 매칭 전에는 다른 참가자의 개인정보를 볼 수 없고, 확정 후에도 제한된 소개(표시 이름·연령대·MBTI·관심사·한 줄 소개)만 볼 수 있어야 한다. 같은 테이블의 못 먹는 음식·알레르기는 이름 없이 테이블 단위 요약으로만 공개한다.INF-04~06
R-11참가자는 행사 1일 전 리마인드(앱 내 알림·웹 푸시·단체방, 설정 시 이메일)와, 행사 시작 시각에 단체방에 자동 게시되는 대화 주제(공통 관심사·대화 성향 기반 3개 이상)·아이스브레이킹 게임을 받을 수 있어야 한다.INF-07, CON-01~03
R-12참가자는 앱에서 체크인할 수 있어야 하고, 행사 후 테이블 분위기·대화·식당 만족도와 재참여·추천 의향을 입력하고, 원하면 다른 참가자를 언급하지 않는 공개 후기를 남길 수 있어야 한다.FDB-01~03
R-13참가자는 다시 만나고 싶은 사람과 만나고 싶지 않은 사람을 비공개로 선택하고, 불쾌한 행동을 신고하고 해당 사용자를 차단할 수 있어야 한다. 신고 내용은 상대에게 공개되지 않아야 한다.FDB-04, SAF-01
R-14참가자는 과거 참가 날짜·지역과 피드백 제출 여부를 확인하고, 이전 지역·날짜 선호와 참가 결과를 반영한 다음 일정 추천을 받아 재신청할 수 있어야 한다.RET-01, RET-02
R-15참가자는 행사 전날까지 앱에서 직접 신청을 취소할 수 있어야 한다. 진행 2일 전보다 앞선 취소는 사전 취소(CANCELED_EARLY)로 자동 환불하고, 진행 2일 전부터 전날까지의 취소는 환불 없이 CANCELED_LATE로 기록한다. 행사 당일에는 취소 대신 불참 알림만 제공하며, 불참 알림은 환불 없이 당일 취소(CANCELED_LATE)로 자동 기록한다. 취소·불참 알림 전에 환불 여부를 안내하고, 전날까지 취소한 참가자는 테이블과 단체방에서 자동으로 빠진다. 단체방 퇴장 기능은 제공하지 않는다.PAY-02, STA-01, 12장
R-16결제를 완료하지 않은 신청자는 매칭 후보에서 제외되고, 결제 방법과 결제 기한을 안내받아야 한다.15장, 14장

4.2 필수 — 자동 매칭·자동 처리

번호요구사항PRD ID
R-17시스템은 회차별 매칭 마감 시각이 되면 운영자가 시작하지 않아도 결제 완료자를 대상으로 자동 매칭을 실행해야 한다.MAT-01
R-18시스템은 필수 조건(결제 완료, 날짜·지역 일치, 4~6명, 최고·최저 나이 차이 8살 이내, 차단·신고·비선호 관계 없음)을 하나라도 위반한 테이블을 확정하지 않아야 하며, 확정 직전에 다시 검증해야 한다.MAT-02, 03, 05, 07
R-19시스템은 나이 조건(필수 조건)을 통과한 조합을 성비 → MBTI 궁합 → 공통 관심사 → 만나고 싶은 사람의 성향 순으로 평가하고, 이전에 만난 사람보다 새로운 사람을 우선해야 한다.MAT-04, 06
R-20시스템은 4명 미만이거나 조건 미충족인 조합을 해제해 신청 범위 안의 다른 미확정 테이블로 재배치하고(5.2 우선순위), 7명 이상 후보군은 4~6인으로 분리, 합쳐 4~6명이 되는 미완성 테이블은 병합해야 한다.MAT-08, 09, STA-03
R-21시스템은 필수 조건을 모두 충족하고 최소 매칭 점수 이상인 4~6인 테이블을 운영자 승인 없이 자동 확정하고, 재배치 후에도 배치되지 못한 참가자를 ALTERNATIVE_OFFERED로 전환해 대체 일정을 추천해야 한다.MAT-10, 11, STA-04
R-22시스템은 확정·재배치·실패 이유와 현재 상태를 참가자와 운영자에게 설명하되, 다른 참가자의 개인정보나 상세 점수는 노출하지 않아야 한다.MAT-12
R-23같은 매칭 작업이 여러 번 실행돼도 중복 테이블·중복 환불·중복 단체방이 생기지 않아야 하고, 같은 참가자를 두 테이블에 동시에 배치하거나 일정 이동 중 결제를 중복 승인하지 않아야 한다.PRD 7.3, 7.4

5.1 필수 조건과 선호 조건

구분조건처리
필수 조건결제 완료, 참가 가능 날짜·희망 지역 일치, 4~6명, 연장자와 막내의 나이 차이 8살 이내, 차단·신고·비선호 관계 없음하나라도 위반하면 확정하지 않고 자동 재배치. 억지로 테이블을 만들기 위해 완화하지 않는다. 확정 이후 행사 당일의 인원 감소는 R-27을 따른다.
선호 조건성비, MBTI 궁합, 공통 관심사, 만나고 싶은 사람의 성향, 새로운 사람 비율조건별 점수를 합산해 가장 좋은 조합을 선택

5.2 자동 재배치 우선순위

  1. 같은 날짜·같은 희망 지역의 다른 미확정 테이블
  2. 같은 날짜·사용자가 선택한 다른 희망 지역의 미확정 테이블
  3. 사용자가 선택한 다른 날짜·같은 희망 지역의 미확정 테이블
  4. 사용자가 선택한 다른 날짜·다른 희망 지역의 미확정 테이블
  5. 위 후보가 없으면 선택하지 않은 모집 일정 중 조건에 맞는 회차를 추천하고, 사용자 동의 후 이동
  6. 이동을 원하지 않으면 이용권 보관 또는 환불 선택 제공

재배치 중에도 필수 조건은 완화하지 않으며, 같은 사용자를 동시에 두 테이블에 배치하지 않고, 재배치가 끝난 뒤에만 확정한다. 이미 확정된 테이블이 행사 당일 3명으로 줄어든 경우는 다시 확정하는 것이 아니므로 R-27에 따라 그대로 진행한다.

기초·시연 데이터가상데이터 294건 정제·적재, 예정 회차, 파트너 식당 재고, 과거 참석·피드백·차단 관계7장

6.2 추가 구현 범위

R-41~R-49. 필수 범위의 E2E 시연이 완성된 뒤 남은 시간에 우선순위대로 구현하고, 구현 여부는 기능 명세서와 테스트 체크리스트에 기록한다. 구현하지 않은 기능의 메뉴·버튼은 화면에 내보내지 않는다.

6.3 제외 범위

제외할 업무범위 설명
실제 PG 결제·환불PG 결제·부분 취소·전체 환불 API 연동(PAY-04, P1)은 하지 않는다. 결제·환불은 상태 전환만 모의 구현한다.
문자·카카오 알림톡발송하지 않는다. 알림톡은 사업자 인증을 마친 비즈니스 채널과 템플릿 사전 심사가 필요해 해커톤에서 갖출 수 없다. 앱 내 알림·웹 푸시·이메일로 대신하고, 정식 운영 때 연결할 수 있게 발송 채널을 분리해 둔다.
카카오톡 단체방 연동카카오는 단체 채팅방을 만드는 공개 API를 제공하지 않고, PRD INF-04와 완료 조건이 앱 내 단체방을 요구하므로 앱 안의 실시간 단체방으로 대신한다.
네이티브 앱이번 범위에서는 앱스토어 배포 앱을 만들지 않는다. 참가자 화면은 모바일 우선 반응형 웹과 PWA(홈 화면 설치·웹 푸시)로 제공하고, 이후 웹뷰·네이티브 앱으로 확장할 수 있게 한다.
소셜 로그인·휴대전화 인증PRD가 허용한 테스트 계정 로그인으로 대신한다.
학습형 추천누적 결과로 가중치를 자동 조정하는 기능(MAT-16, P2)은 하지 않는다.
실제 식당 예약 연동파트너 식당과 수용 인원은 데이터로 관리하고, 외부 예약 시스템과 연동하지 않는다.
성장 시나리오 기능멤버십 상품, 지자체·기관 프로그램, 아시아권 확장, 다국어는 다루지 않는다.

7. 데이터 및 구현 조건

구분조건
구현 스택Next.js(App Router) + TypeScript + Supabase(Postgres·Auth·Realtime·pg_cron) + Vercel, 이메일은 Gmail SMTP — ADR-001
화면참가자 화면은 휴대폰 화면을 기준으로 설계한 반응형 웹으로, 태블릿·PC에서는 2열 배치로 넓혀 쓰고 PWA로 홈 화면에 설치할 수 있게 한다. 운영자 화면(/admin)은 PC 기준으로 제공한다. 두 화면은 하나의 앱에 있다.
알림 발송앱 내 알림은 항상 기록하고, 웹 푸시와 이메일(Gmail SMTP, 보낸 사람 이름 "우연한 식탁")은 참가자 설정에 따라 보낸다. 일괄 생성한 테스트 참가자의 가상 주소로는 보내지 않는다.
기초 데이터와썹하우스 신청서 응답 294건(가상데이터)을 정제해 적재한다 — MBTI 대문자 16종 정규화, 자유 입력 지역을 표준 지역(홍대/합정·강남/신논현·을지로/종로·잠실 + 기타)으로 매핑, 날짜 문자열 정리, 나이를 출생연도로 변환, 비어 있는 직업·연락처는 가상 값으로 채운다.
시연 데이터예정 회차(목요일 저녁), 파트너 식당과 수용 인원, 과거 참석·피드백·차단 관계를 만들어 재배치·실패·피드백 반영을 시연할 수 있게 한다.
상태 저장5.3의 4종 상태를 각각 저장하고, 상태가 바뀔 때마다 시각·주체·원인·이전 값을 기록한다.
계정참가자 테스트 계정과 운영자 테스트 계정을 제공하고 제출 메시지에 기재한다. 운영자 기능은 운영자 역할에만 열린다.
시간 기준한국 표준시(KST). 매칭 마감 시각은 회차별로 설정하고, 시연을 위해 운영자 화면에서 즉시 실행할 수 있다.
수치 기준자료 간 수치가 다르면 PRD v0.2를 기준으로 한다.
테스트 정보연락처·이름 등은 가상의 값만 사용하고 실제 개인정보를 넣지 않는다.

8. 비기능 요구사항

항목요구사항
개인정보·안전연락처·생년·차단·신고·사람별 선호는 운영상 필요한 사용자에게만 공개한다. 매칭 전에는 다른 참가자 정보를 공개하지 않는다. 운영자 계정은 권한별로 접근을 통제하고 주요 변경 이력을 남긴다. 개인정보 삭제 요청과 탈퇴 후 보관 정책을 문서로 정의한다. 못 먹는 음식·알레르기는 같은 테이블에도 이름 없이 테이블 단위 요약으로만 공개하고, 광고성 소식은 이메일로 보내지 않는다.
사용성모바일 화면을 우선 설계하고 큰 화면에서는 배치를 넓힌다. 최초 신청은 프로필 입력을 포함해 5분 안에 끝나야 한다. 홈에서 현재 상태를 바로 확인하고, 실패·대기 상태에서도 다음 행동을 한 화면 안에서 고를 수 있어야 한다.
신뢰성매칭·환불·단체방 생성은 다시 실행해도 결과가 중복되지 않는다. 필수 조건은 확정 판단에서 어떤 경우에도 완화하지 않는다(확정 이후 당일 인원 감소는 R-27). 대체 일정 이동과 환불은 시스템이 임의로 정하지 않고 참가자가 고른다.
운영·추적매칭 알고리즘 버전·적용 기준·생성·분리·병합·재배치·확정 결과, 자동 처리 실패 사유와 운영자 개입 이력, 메시지 발송 성공·실패·재시도, 일정 이동·보관·환불 처리 결과를 기록한다. 참가자 목록과 테이블 결과를 CSV로 내보낼 수 있어야 한다.
가용성제출한 배포 링크는 결과 발표(10/29)까지 접속 가능해야 한다.
구현 범위 일치화면에 보이는 메뉴·버튼은 모두 구현된 화면과 동작으로 이어진다.

9. 주요 사용자 시나리오

9.1 신청부터 확정·식사까지 (참가자 정상 흐름)

  1. 참가자가 테스트 계정으로 로그인하고 프로필·매칭 선호·식사 조건을 입력한다.
  2. 모집 중인 회차에서 참가 가능한 날짜와 희망 지역을 복수 선택하고, 이용권을 고른 뒤 모의 결제한다.
  3. 홈 화면에서 "매칭 대기"와 발표 예정 시점을 확인한다.
  4. 마감 시각에 시스템이 자동 매칭을 실행하고, 조건을 충족한 테이블을 자동 확정한다.
  5. 참가자는 확정 알림을 받고 식당·집합 시간·단체방 공지를 확인한다.
  6. 행사 1일 전 리마인드, 행사 시작 시각에 대화 주제와 아이스브레이킹이 단체방에 게시된다.
  7. 참가자가 체크인하고 식사한 뒤 만족도·사람별 선호를 제출한다.

9.2 매칭 실패와 해결

  1. 최초 조합이 4명 미만이 되어 시스템이 다른 테이블로 재배치를 시도한다.
  2. 신청 범위 안에서 테이블을 찾지 못한 참가자는 ALTERNATIVE_OFFERED 상태가 되어 이유와 대체 일정을 확인한다.
  3. 참가자가 대체 일정을 고르면 결제를 유지한 채 새 회차 매칭 대기로 이동하고, 환불을 고르면 운영자 개입 없이 환불 완료 상태가 된다.
  4. 확정된 테이블에서 행사 전날까지 한 명이 취소해 3명이 되면, 남은 참가자는 조건에 맞는 다른 테이블로 자동 재배치된다(당일이면 3명으로 진행).

9.3 운영자 흐름

  1. 운영자가 회차·지역·마감 시각과 식당 재고를 설정하고, 마감 전 매칭 미리보기로 예상 테이블 수와 실패 예상자를 확인한다.
  2. 대시보드에서 자동 매칭·재배치·확정 결과와 핵심 지표를 확인한다.
  3. 예외 처리함에는 식당 부족·조건 충돌·발송 실패처럼 자동 해결되지 않은 건만 나타나고, 운영자는 그 건만 처리한다.

9.4 재방문 — 피드백이 반영된 다음 매칭

  1. 참가자가 참가 이력에서 다음 일정 추천을 보고 재신청한다.
  2. 다음 매칭에서 이전에 만난 사람보다 새로운 사람이 우선되고, 다시 만나고 싶지 않다고 한 사람·신고 관계는 같은 테이블에서 제외된다.
